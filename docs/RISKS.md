# Known Risks & Mitigations

| # | Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| 1 | Parsers break when a source changes markup/format | High | Ingestion silently stops | Prefer API/RSS sources (structured, stable); `last_run_status = empty` → Sentry alert; per-source isolation so one broken source doesn't stop the rest |
| 2 | Source rate limits / bans | Medium | Loss of a source | Gentle cadence (once per 4h), caching, exponential backoff, honest User-Agent; respect `Retry-After` |
| 3 | Free hosting puts containers to sleep | High | Missed ingestion runs, slow cold starts | **Hit in practice**: GitHub Actions ran the `*/10` keep-alive only every 4–5 h (Oct 2026). The 10-minute tick now comes from Supabase `pg_cron` (ADR-023) and doubles as keep-alive; GitHub workflows stay as a fallback. If pg_cron is ever unavailable, any free HTTP cron (cron-job.org) can call the same hook. `DB (prod)` → `schedule:status` shows the last runs and HTTP answers |
| 4 | Free LLM tiers exhausted (real limit is tokens/day, not requests/day) | Medium (phase 4) | Scoring/summarization stalls | Failover across providers (Groq / OpenRouter / Gemini — ADR-005); batch scoring; summarize context to cut tokens; degrade gracefully to rules-based matching. Groq's free tier also caps tokens *per minute* (8000, output budget included): one digest call stays ~4k (12 cards), calls are paced 30 s apart, and a failed instant push retries for up to 6 h instead of dropping the window (v2.0.2) |
| 5 | Scope creep | High | v1.0 never ships | Hard rule: phase N+1 only after current phase is deployed; "out of scope" list in PRODUCT.md |
| 6 | Free-tier limits change or products shut down | Low | Migration required | All infra choices are commodity (Postgres, Redis, SMTP-like email API) — swappable; no vendor-specific features in core logic |
| 8 | Background schedulers burn the Upstash free-tier command budget (500k/mo) | Medium | Queue-backed background work stalls when the budget runs out | **Hit in practice**: the first `planner:tick` on BullMQ reached ~247k/500k within days — BullMQ's worker polls Redis continuously even when idle. Fixed in v1.10.1 by moving the tick to a plain in-process `setInterval` (no Redis; revised ADR-015 §7). The ingestion worker's own idle polling was then found to be the real steady consumer (BullMQ blocks on Redis 24/7); tuned in v1.10.3 (`drainDelay` 60s, `stalledInterval` 5min → ~12× fewer idle commands). Keep an eye on the Upstash dashboard; if ingestion polling ever creeps up, the same treatment applies where a job doesn't truly need a distributed queue |
| 9 | A 10-minute tick multiplies per-cycle costs (ADR-023) | Medium | Supabase egress, LLM quotas or Upstash commands run out | Only due sources are enqueued (idle tick = no Redis commands); dedup reads only companies with fresh vacancies; the LLM résumé pass stays at 4 h. Watch Supabase egress and the Upstash dashboard after the switch |
| 10 | Strangers' resumes reach a free LLM tier that trains on submitted data (phase 5) | Medium | Personal data leak, trust | Non-owner resume analysis uses only providers that do not train on free-tier data (ADR-025 §4); `/privacy` names the provider; `/delete` removes everything |
| 11 | Formula scoring is worse than the LLM verdict (phase 5) | Medium | Users see noise and leave | Precision ≥ 70% of the formula's top 20 rated ≥80 by the LLM on the author's `resume_matches` (ADR-026; 85% on 2026-10-15); precision does not measure recall; synonym dictionary; `formula:check` in `DB (prod)`. The card no longer has 👍/👎 (v1.28.0), so feedback weights barely move; per-user tuning is now `/settings` filters and the minimum fit |
| 12 | Bot API rate (≈30 msg/s overall, 1/s per chat) with many users after one ingestion run (phase 5) | Medium | Lost or late cards | One send limiter, `429 retry_after`, `403 blocked` turns the digest off (ADR-024 §9). In place since v1.28.0. The run is sequential, so one per second per chat means a user with 60 new cards holds the tick for a minute; parallel sends across chats are the fix if many users wait |
| 13 | A source's owner objects to its vacancies reaching other people (phase 5.4) | Low | A source must be dropped for non-owners, or entirely | Terms re-read per source (DATA_SOURCES.md, "Who receives which source"); every card links to the posting and names the source; `sources.config.ownerOnly: true` takes a source away from non-owners with a seed change and `DB (prod)` → `migrate` |
| 7 | Author burnout / life happens | Medium | Project stalls | Small deployable phases; each phase leaves the project in a usable, resume-worthy state |

Review this table at the end of each phase; add new risks as they surface.
